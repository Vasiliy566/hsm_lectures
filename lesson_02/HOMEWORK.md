# Домашняя работа: довести coding agent до GitHub

Возьмите код из [`starter`](starter) и расширьте его инструментами для
проверяемой работы с реальным Git-репозиторием.

## Что добавить

### 1. README в начальном контексте

До первого запроса к модели найдите корневой `README.md`, безопасно прочитайте
его и добавьте в контекст задачи. Если README отсутствует, передайте модели этот
факт явно.

### 2. Проверка репозитория до запуска агента

До изменения файлов выполните `git status --short` и `git diff`. Покажите
существующий diff пользователю и добавьте его в контекст LLM. Если рабочее дерево
уже содержит изменения, агент не должен молча перезаписывать их: запросите
подтверждение или завершите работу.

### 3. Новые tool calls

Реализуйте как отдельные типизированные tools:

- `run_tests` — запускает настоящие тесты с timeout;
- `git_diff` — возвращает ограниченный по размеру diff;
- `git_commit` — добавляет только явно перечисленные файлы и создаёт commit;
- `git_push` — отправляет текущую учебную ветку в `origin`.

Нельзя давать модели универсальный shell-tool, принимать строку команды или
использовать `eval`.

## Approval policy

- `git_diff` — read-only, подтверждение не требуется;
- `run_tests` — требует подтверждения, потому что запускает код репозитория;
- `git_commit` — требует отдельного подтверждения после показа diff;
- `git_push` — требует отдельного подтверждения непосредственно перед отправкой.

`commit` и `push` нельзя объединять в один tool. Запрещены push в `main`/`master`
и любые варианты `--force`.

Если пользователь отказал, верните отказ модели как обычный `function_result`:

```json
{"ok": false, "error": "User denied approval"}
```

## Обязательный workflow

```text
прочитать README
→ показать исходные git status + git diff
→ изучить файлы
→ внести изменение после approval
→ запустить тесты после approval
→ показать итоговый git diff
→ commit после approval
→ push после отдельного approval
```

## Definition of Done

Агент может сообщить об успехе, только если:

- README был добавлен в начальный контекст;
- исходный diff был проверен до изменения;
- тесты действительно запускались и завершились успешно;
- пользователь увидел итоговый diff;
- commit создан в отдельной ветке;
- получен commit SHA;
- push подтверждён и завершился успешно.

Если push отклонён пользователем, корректный результат — локальный commit и
явное сообщение `push не выполнен`, а не заявление о полном успехе.

## Что сдать

Проверьте минимум два сценария: полный успешный путь и отказ пользователя от
`git_push`.
